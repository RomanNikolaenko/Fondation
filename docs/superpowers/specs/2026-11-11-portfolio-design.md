# Специфікація: Портфель і ребалансування (частина 3)

Дата: 2026-11-11. Статус: затверджено. Залежність: частина 1 (ядро свінг-бота).

## 1. Мета

Довгостроковий портфель поверх наявного конвеєра: користувач задає цільові
ваги тікерів, рушій за розкладом (перший торговий день місяця або кварталу)
порівнює цілі з фактичними вагами і через звичайну чергу схвалення створює
наміри «докупити / продати до цілі». Портфель — окреме джерело угод, яке не
втручається у swing-стратегії: їх об'єднують лише спільні ризик-ліміти
(вільний кеш, сукупна експозиція, ліміт ордерів на день).

## 2. Принципи

1. **Один конвеєр.** Ребаланс-наміри живуть у тому самому життєвому циклі,
   що й swing-наміри: `PendingApproval`/`Approved` → `Submitted` →
   `Filled`/`Expired`/… Схвалення — на наявному екрані «Схвалення».
   Ордери повз конвеєр не надсилаються.
2. **Чистота функцій.** Математика ребалансу (цілі + позиції + ціни →
   дельти) — чиста функція в `fond-core`, покрита юніт-тестами; рушій лише
   застосовує її до живих даних.
3. **Не заважати стратегіям.** Ваги портфеля живуть у власній секції конфігу;
   swings користуються своїми частками. Спільні — тільки ліміти ризику.
4. **Без сюрпризів.** Дрібні дельти (нижче порогів) не створюють ордерів;
   продажі виконуються перед купівлями (звільняють кеш); купівлі — строго
   в межах вільного кешу; добова квота ордерів спільна зі swing.
5. **У бек-тесті ребалансування не входить** (v1): бек-тестер оцінює лише
   swing-стратегії. Портфельна логіка в бек-тесті — окреме рішення пізніше.

## 3. Конфігурація (`[portfolio]` у `config.toml`)

```toml
[portfolio]
enabled = false            # за замовчуванням вимкнено
rebalance = "off"          # "off" | "monthly" | "quarterly"
drift = 0.05               # поріг: |ціль − факт| ≥ 5% equity, інакше пропуск
min_order_usd = 100        # дельти дешевше цього не стають ордерами
[portfolio.targets]        # карта тікер → вага (частка equity)
SPY = 0.5
AAPL = 0.2
```

Валідація (`EngineConfig::validate`): кожна вага в `(0, 1]`; сума ваг ≤ `1`
(залишок — кеш або swing-стратегії); `drift` у `(0, 0.5]`; `min_order_usd`
≥ `1`; `rebalance` — лише три дозволені значення; при `enabled = true`
вимагається `rebalance != "off"`. Порушення — українські повідомлення.

## 4. Розклад

Тригер живе всередині вечірнього аналізу (крок `Analysis`) — окремого кроку
розкладу немає. Ребаланс виконується, якщо сьогодні за ET **перший торговий
день** місяця (`monthly`) або кварталу — січня/квітня/липня/жовтня
(`quarterly`), і `portfolio.enabled = true`. Дата сесії визначається за
торговим календарем (не «перше число» наївно).

Ручний запуск поза розкладом — екран «Портфель», кнопка «Ребалансувати зараз»
(202 у фоні; одночасно лише один запуск — 409; працює під `job_lock`, як
ручний AI-аналіз).

## 5. Математика дельт (чиста функція, `fond-core`)

Вхід: цілі (map), позиції (qty × ціна останнього бару), equity, ціни,
`drift`, `min_order_usd`. Вихід: `Vec<RebalanceDelta { symbol, side, qty,
limit_price, target_value, current_value }>` — відсортований: продажі
спочатку (за спаданням дельти), потім купівлі (за спаданням).

- `target_value = вага × equity`; `current_value = qty × ціна`;
  `delta = target_value − current_value`.
- Пропуск дельти, якщо `|delta| < max(drift × equity, min_order_usd)`.
- Купівля: `qty = ⌊delta / ціна⌋`; `limit_price = ціна × (1 + max_gap)`
  (`max_gap` з `RiskConfig`). Пропуск, якщо `qty = 0`.
- Продаж: не більше наявної кількості; `limit_price = ціна × (1 − max_gap)`.
- Купівлі обрізаються послідовно під доступний кеш (списання buy-дельт
  зменшує залишок); якщо кешу не вистачає — купівля пропускається з журналом.
- Тікер цілі без барав → пропуск із журналом «немає ціни».

## 6. Наміри і конвеєр

- `fond-core`: `IntentKind::Rebalance { side: Side, qty: u32,
  limit_price: Decimal }`; `IntentTag::Rebalance` →
  `…-portfolio-SYMBOL-rebalance`; стратегія наміру — `portfolio`.
- Створення: статус за режимом виконання (`PendingApproval` /
  `Approved`), як у swing-входів; пояснення українською з дельтою
  («докупити до цілі 20%: +$1 250» / «продати до цілі 10%: −$900»).
- Схвалення/відхилення — наявні ендпойнти `approve`/`reject` без змін.
- Submit (`run_pre_open_submit`): порядок черги
  `MoveStop < Exit < Rebalance(продаж) < Rebalance(купівля) < Entry`;
  ордер — Limit Day (buy: `limit_price`, sell: `limit_price`), без
  стоп-леги; квота `max_orders_per_day` спільна.
- Звірка: крок 1 обробляє `Rebalance`-інтенти — виконана купівля створює
  tracked-позицію зі стратегією `portfolio` і без стопа; виконаний продаж
  зменшує кількість (нуль → позиція закрита). `check_stop` для позицій
  стратегії `portfolio` не намагається «відновити» стоп-легу.

## 7. Журнал

Події ребалансу пишуться в наявні типи журналу: `Intent` (створення
намірів), `Order`/`Fill` (відправлення/виконання), `Cycle` (підсумок
проходу: «ребаланс: 2 купівлі, 1 продаж, 3 пропущено за порогом»).

## 8. API (`fond-api`, fond-engine)

- `POST /portfolio/rebalance/run` → `202` з `RebalanceRunQueuedDto { date }`;
  фонова задача під `job_lock` + mutex `portfolio` у `Jobs` (повторний
  запуск — `409`). Якщо сьогодні не день ребалансу — ручний запуск все одно
  дозволений (оператор вирішує сам).
- DTO: `RebalanceRunQueuedDto`; поточні ваги UI обчислює з `/positions`
  і `/account`, цілі бере з конфігу.

## 9. Інтерфейс (екран «Портфель»)

- Таблиця: тікер, ціль %, поточна вага %, відхилення (пп), оціночна дельта $,
  факт позиції (qty).
- Редактор цілей: додати/видалити тікер, вага у відсотках; підсумок суми
  з підсвіткою понад 100%; збереження через звичайний `putConfig`.
- Кнопка «Ребалансувати зараз» (disabled поки йде запуск), повідомлення
  «запущено у фоні», живе оновлення через журнал-події; 409 — помилкою.
- Навігація: пункт «Портфель» після «Позиції». Порожній стан: «цілі не
  задані — додайте тікер і вагу».

## 10. Що не входить

- Ребалансування в бек-тесті (v1, розділ 2.5).
- Дивіденди, дроблення, податковий облік.
- Автопідписка нових цілей; цілі задає лише оператор.
- Живий режим і IBKR — окремі підпроєкти.
