# Fond — Частина 1: ядро торгового бота і свінг-торгівля

- **Дата:** 2026-11-04
- **Статус:** чернетка на перевірку
- **Обсяг документа:** лише частина 1 (див. розділ 3)

## 1. Мета і контекст

### Що сказав користувач
- Потрібен **автоматичний торговий бот** для фондового ринку.
- Мають бути всі три стилі торгівлі: свінг (дні–тижні), внутрішньоденна торгівля, довгостроковий портфель. Порядок реалізації: ядро + свінг → портфель → внутрішньоденна.
- Логіка рішень: **правила на індикаторах + фільтр новин на LLM**.
- Режим виконання перемикається: **«з підтвердженням»** або **«авто»**.
- Інструменти: **базовий список (S&P 500 + ETF) + щоденний сканер**, власні тікери можна додавати й виключати.
- Інтерфейс: **десктопний застосунок**.
- Стек: **Rust + Tauri + Angular**, pnpm, Oxfmt, Oxlint, Stylelint, rustfmt.

### Погоджені рішення (запропоновані асистентом і схвалені)
- Брокер: старт на **Alpaca paper trading**, реальна торгівля пізніше через **Interactive Brokers** (окремий підпроєкт). Брокер підключається через адаптер.
- Окремий фоновий рушій `fond-engine`, а Tauri-застосунок працює як його клієнт.
- Дві стратегії, лише купівля, ринковий фільтр SPY.
- Ліміти ризику за замовчуванням, аварійна зупинка, звірка з брокером (розділ 9).
- До rustfmt додано clippy.

### Чим цей застосунок не є
Застосунок не прогнозує ринок і не гарантує прибутку. Він автоматизує виконання прозорих правил, перевіряє їх на історії і жорстко обмежує ризик. Застосунок не дає фінансових порад, і рішення про використання реальних грошей ухвалює користувач.

### Критерій успіху частини 1
Рушій щодня, без нагляду, проходить повний цикл на Alpaca paper. Кожне рішення пояснене в журналі. Бектест чесно показує, як стратегії поводилися на історії, разом з обмеженнями оцінки (деталі в розділі 18).

## 2. Обсяг частини 1

**Входить:**
- Cargo workspace, рушій `fond-engine` з локальним API, десктоп Tauri + Angular.
- Завантаження і кешування денних свічок (Alpaca Market Data).

**Не входить** (окремі підпроєкти):

- Внутрішньоденна торгівля і дані в реальному часі (частина 3).
- Короткі позиції (шорти), опціони, криптовалюти.
- Telegram, веб-доступ, мобільний застосунок.
- Оптимізатор параметрів (перебір сіткою). У частині 1 параметри задаються вручну.

## 4. Архітектура

### 4.1 Процеси
```
┌──────────────────────────── Windows ────────────────────────────┐
│  Fond Desktop (Tauri)                fond-engine (фоновий)      │
│  ┌──────────────┐  Tauri cmds  ┌────────────┐  HTTP + WS   ┌────────────────────┐
│  │ Angular UI   │ ───────────▶ │ src-tauri  │ ───────────▶ │ axum API           │
│  │ (webview)    │ ◀─────────── │ (Rust)     │ ◀─────────── │ планувальник       │
│  └──────────────┘   events     └────────────┘ 127.0.0.1    │ оркестрація циклу  │
│                                                  + токен   │ SQLite             │
│                                                            └─────────┬──────────┘
└──────────────────────────────────────────────────────────────────────┼───────────┘
                                                                       │ HTTPS
                                              Alpaca (paper + data) · Claude API · Finnhub
```

- `fond-engine` — окремий бінарник без вікна. Закриття або падіння вікна не зупиняє торгівлю.
- **Один екземпляр.** Рушій бере ексклюзивний lock-файл у каталозі даних. Другий екземпляр завершується з помилкою. Це критично, бо два рушії подвоїли б угоди.
- **Запуск рушія.** Tauri-застосунок перевіряє `GET /health`. Якщо рушій не відповідає, застосунок запускає його як від'єднаний процес (sidecar), щоб він пережив закриття застосунку.
- **Автозапуск** (опція в налаштуваннях): рушій і застосунок (згорнутий у трей) реєструються в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Права адміністратора не потрібні.
- **Закриття вікна** згортає застосунок у трей. Пункт трею «Вийти» закриває лише застосунок, і рушій працює далі. Застосунок про це попереджає.

### 4.2 Зв'язок
- Angular спілкується лише з Tauri (команди та події). Бекенд Tauri звертається до рушія через HTTP і WebSocket.
- Рушій слухає тільки `127.0.0.1`. Кожен запит містить заголовок `Authorization: Bearer <token>`.
- Токен генерується під час першого запуску рушія і зберігається у Windows Credential Manager. У webview він не потрапляє.
- DTO API описані в крейті `fond-api`. TypeScript-типи для Angular генеруються з Rust через `ts-rs`, тож зміна контракту ламає компіляцію фронтенду, а не роботу застосунку. (`tauri-specta` відкинуто: на листопад 2026 він досі в стадії release candidate.)

### 4.3 Cargo workspace

|---|---|---|

### 4.4 Головний принцип
Стратегія — це чиста функція від даних. Вона отримує свічки **лише до дня рішення включно** і повертає сигнал. Про брокера, час чи мережу стратегія нічого не знає. Тому той самий код стратегії працює в бектесті, на paper-рахунку і в майбутньому live-режимі.

## 5. Доменна модель і трейти (ескіз)

```rust
// fond-core — ескіз, остаточні сигнатури визначаються в плані
pub struct Bar { pub date: NaiveDate, pub open: f64, pub high: f64, pub low: f64, pub close: f64, pub volume: f64 }

pub struct EntrySignal {
    pub strategy: StrategyId,
    pub symbol: Symbol,
    pub signal_date: NaiveDate,
    pub reference_price: f64,     // close дня сигналу
    pub stop_price: f64,
    pub take_profit: Option<f64>, // None → OTO (вхід + стоп), Some → bracket
    pub strength: f64,            // 0..1, для впорядкування кандидатів
    pub explanation: String,      // людською мовою, для журналу та UI
}

pub enum ExitDecision { Hold, Exit { reason: String }, MoveStop { new_stop: f64, reason: String } }

pub trait Strategy: Send + Sync {
    fn id(&self) -> StrategyId;
    fn warmup_bars(&self) -> usize;
    /// `bars` закінчується днем рішення; доступу до майбутнього немає за побудовою.
    fn evaluate_entry(&self, ctx: &MarketContext, symbol: &Symbol, bars: &[Bar]) -> Option<EntrySignal>;
    fn evaluate_exit(&self, ctx: &MarketContext, position: &Position, bars: &[Bar]) -> ExitDecision;
}

#[async_trait] pub trait Broker      { account, positions, open_orders, submit(OrderRequest), cancel, replace_stop, order_by_client_id }
#[async_trait] pub trait MarketData  { daily_bars(symbols, from, to), calendar(from, to), latest_trade(symbol), assets() }
#[async_trait] pub trait NewsSource  { news(symbol, since) -> Vec<NewsItem> }
#[async_trait] pub trait EarningsCalendar { next_earnings(symbol, from) -> Option<NaiveDate> }
#[async_trait] pub trait NewsJudge   { judge(NewsJudgeRequest) -> Result<NewsVerdict> }
pub trait Clock: Send + Sync { fn now(&self) -> DateTime<Utc>; }
```

- `MarketContext` містить дату рішення і стан ринкового фільтра (SPY відносно SMA200).
- Ціни ордерів і грошові суми зберігаються в `rust_decimal::Decimal`. Індикатори рахуються в `f64`, а перехід у `Decimal` відбувається в одному місці, під час формування ордера, з округленням до кроку ціни.
- Індикатори пишемо самі, їх небагато: SMA, RSI (Wilder), ATR (Wilder), максимум і мінімум за N днів, середній обсяг, середній оборот. Кожен покривається тестами з еталонними значеннями.

## 6. Щоденний цикл (свінг)

Усі моменти зберігаються в UTC. Розклад задається в часі біржі (America/New_York), а UI показує ET і київський час. Торгові дні та скорочені сесії береться з календаря Alpaca.

| # | Коли (ET, за замовчуванням) | Крок |
|---|---|---|
| 1 | 16:30, торговий день | **Дані:** перезавантажити денні свічки (скориговані на спліти й дивіденди) за останні ~600 календарних днів для всього списку, SPY і відкритих позицій. Вікно перезаписується повністю, бо скориговані ціни змінюються заднім числом. Повна історія для бектесту (з 2016 року) завантажується окремою дією на екрані «Бектест» |
| 2 | одразу після 1 | **Сканер:** ціна ≥ $5, середній оборот за 20 днів ≥ $20 млн, актив `tradable` і `active` в Alpaca, історія ≥ 250 свічок |
| 3 | одразу після 2 | **Виходи:** `evaluate_exit` для кожної відкритої позиції → намір закрити або намір підтягнути стоп |
| 4 | одразу після 3 | **Входи:** `evaluate_entry` для кандидатів, лише якщо ринковий фільтр дозволяє |
| 5 | одразу після 4 | **Фільтр звітів:** звіт протягом найближчих 3 торгових днів → блок |
| 6 | одразу після 5 | **Фільтр новин (Claude):** `allow` / `caution` / `block` з причинами |
| 7 | одразу після 6 | **Ризик-менеджер:** розмір позиції, ліміти; сигнали впорядковуються за `strength`, поки є місце |
| 8 | одразу після 7 | **Наміри:** намір на вхід у режимі «з підтвердженням» отримує статус `pending_approval`, у режимі «авто» — `approved`. Наміри на вихід і підтягування стопа завжди отримують `approved` без схвалення, бо вони зменшують ризик. Сповіщення про нові угоди на схвалення |
| 9 | 08:55 наступного торгового дня | **Дедлайн схвалення:** непідтверджені наміри отримують статус `expired` |
| 10 | 09:00 | **Перевірка перед відкриттям:** звірка з брокером, стан паузи й аварійної зупинки, ліміти збитку, перевірка ціни |
| 11 | 09:00–09:25 | **Відправка:** ордери на вхід, вихід і зміну стопа (розділ 6.1) |
| 12 | щогодини 09:30–16:00 | **Звірка:** позиції, ордери, виконання; оновлення журналу; сповіщення про виконання і спрацювання стопів |

Якщо рушій пропустив крок (комп'ютер був вимкнений), під час старту він доганяє: дані, звірку і аналіз. Він **не** відправляє ордери на вхід за сигналами, що застаріли: сигнал дійсний лише для найближчої торгової сесії після дня сигналу.

### 6.1 Ордери
- **Вхід:** лімітний ордер з `time_in_force = day`, ліміт = `reference_price × (1 + max_gap)`, де `max_gap` за замовчуванням 1%. Він захищає від купівлі після великого гепу вгору. Якщо ордер не виконався за день, він скасовується автоматично.
- **Клас ордера:** `bracket`, якщо стратегія дала `take_profit`, інакше `oto` (вхід + стоп-лос). Стоп завжди зберігається у брокера.
- **Підтягування стопа:** заміна (replace) ціни стоп-ордера лише в бік зменшення ризику, тобто вгору для довгої позиції.
- **Вихід за сигналом:** скасувати стоп-ордер, потім подати ринковий ордер на продаж на відкритті. Якщо скасування не підтвердилось, продаж не відправляється, а подія потрапляє в журнал і сповіщення.
- **Ідемпотентність:** `client_order_id = fond-{intent_id}-{leg}`, де `intent_id` стабільний для пари (стратегія, символ, дата сигналу). Перед повтором після збою виконується пошук за `client_order_id`.
- Точні обмеження Alpaca (дозволені TIF для bracket/OTO, поведінка ордерів, поданих до відкриття) перевіряються під час планування (розділ 17).

## 7. Стратегії

Усі стратегії лише купують. Параметри нижче — значення за замовчуванням, усі налаштовуються.

### 7.1 Ринковий фільтр
Якщо закриття SPY нижче його SMA200, нових входів немає жодній стратегії. На виходи фільтр не впливає.

### 7.2 «Відкат у тренді» (`trend_pullback`)
- **Умова тренду:** `close > SMA200` і `SMA50 > SMA200`.
- **Вхід:** `RSI(2) < 10`.
- **Стоп:** `close − 2.0 × ATR(14)`.
- **Ціль:** немає (OTO).
- **Вихід:** `close > SMA5` або минуло 10 торгових днів утримання.
- **Сила сигналу:** тим вища, чим нижчий RSI(2) і чим сильніший тренд (нормовано до 0..1).

### 7.3 «Пробій» (`breakout`)
- **Вхід:** `close > максимуму high за попередні 55 днів` і `volume > 1.5 × середнього обсягу за 20 днів`.
- **Стоп:** `close − 2.0 × ATR(14)`.
- **Ціль:** немає (OTO).
- **Супровід:** щодня стоп = `max(поточний стоп, мінімум low за 20 днів)`.
- **Вихід:** спрацювання стопа (на боці брокера).
- **Сила сигналу:** співвідношення обсягу та відстань пробою в ATR.

### 7.4 Конфігурація
- Кожна стратегія має `enabled` і частку капіталу `allocation` (сума ≤ 100%).
- Нова стратегія додається як новий тип, що реалізує `Strategy`, і реєструється в реєстрі стратегій рушія.
- На один символ — не більше однієї позиції. Якщо позиція вже відкрита, нові сигнали на цей символ відкидаються з причиною. Якщо обидві стратегії дали сигнал на той самий символ, береться сигнал із більшою `strength`.

## 8. Бектест

- **Подієвий прогін** по днях з тими самими `Strategy`, ринковим фільтром, ризик-менеджером і сканером, що й у живому циклі. Відмінності лише в даних і брокері.
- **Симулятор брокера:**
  - Вхід виконується на `open` дня t+1, якщо `open ≤ ліміту`, інакше ордер не виконано.
  - Стоп спрацьовує, коли `low ≤ stop`, за ціною `min(open, stop)`, тобто з урахуванням гепу вниз.
  - Ціль спрацьовує, коли `high ≥ target`. Якщо за день зачеплено і стоп, і ціль, першим вважається стоп.
  - Проковзування за замовчуванням 5 б.п. на кожне виконання. Модель комісій налаштовується (для Alpaca 0).
- **Без «підглядання в майбутнє».** Стратегія структурно отримує лише `&bars[..=t]`. Окремий тест перевіряє, що рішення до дня t однакові на повних і на обрізаних даних.
- **Метрики:** CAGR, максимальна просадка та її тривалість, Sharpe, Sortino, частка прибуткових угод, profit factor, середній виграш і програш, середня тривалість угоди, кількість угод, час у ринку. Бенчмарк — купівля й утримання SPY за той самий період.
- **Навчальний і перевірочний періоди.** Користувач задає дату розділення, і звіт показує метрики для обох частин окремо та разом.
- **Обмеження, які звіт показує прямо:**
  - survivorship bias: використовується поточний склад списку;
  - LLM-фільтр у бектесті вимкнений (модель знає майбутнє відносно історичних дат);
  - фільтр звітів працює, лише якщо джерело дає історичні дати (розділ 17).
- **Результати** зберігаються в SQLite: прогін, угоди, крива капіталу. Їх можна переглядати в UI.

## 9. Ризик-контроль і безпека

### 9.1 Розмір позиції
`qty = floor( equity × risk_per_trade / (entry_limit − stop) )`, після чого діють обмеження:
- вартість позиції ≤ `max_position_pct × equity`;
- вартість позиції ≤ вільних коштів (без плеча);
- `qty ≥ 1`, інакше сигнал відкидається з причиною.

`allocation` стратегії обмежує сумарну вартість відкритих позицій цієї стратегії, а не ризик однієї угоди.

### 9.2 Ліміти (за замовчуванням)
| Ліміт | Значення | Дія при порушенні |
|---|---|---|
| `risk_per_trade` | 1% капіталу | основа розрахунку розміру |
| `max_open_positions` | 10 | нові входи відкидаються |
| `max_position_pct` | 15% | розмір зменшується |
| `max_sector_pct` | 30% | вхід відкидається |
| `max_gross_exposure` | 100% | вхід відкидається |
| `daily_loss_limit` | 3%: капітал на закриття останнього торгового дня впав на ≥ 3% відносно попереднього закриття | наступної сесії нових входів немає (перевірка о 09:00 ET) |
| `weekly_loss_limit` | 6% від капіталу на початок тижня | пауза до ручного відновлення |
| `max_orders_per_day` | 20 | решта ордерів блокується, сповіщення, пауза |
| `price_sanity_pct` | 5% | ордер відхиляється, якщо ліміт відрізняється від останньої ціни більш ніж на цей відсоток |

- **Сектори** беруться з колонки `sector` у файлі списку. Для доданих вручну тікерів сектор підтягується з Finnhub (профіль компанії), а якщо не вдалося, ставиться `Unknown`. `Unknown` — окремий кошик із тим самим лімітом. Кожен широкий індексний ETF є окремим кошиком, а секторні ETF рахуються у свій сектор.

### 9.3 Аварійна зупинка і автопауза
- **Аварійна зупинка** (кнопка в UI і в треї, з підтвердженням) має два варіанти:
  - **без закриття позицій:** скасувати всі відкриті ордери, **крім** захисних стопів наявних позицій, і перевести рушій у стан аварійної зупинки. Позиції залишаються під захистом стопів у брокера;
  - **із закриттям позицій:** скасувати всі ордери, включно зі стопами, і закрити всі позиції ринковими ордерами.
- **Автопауза з сповіщенням** вмикається, коли:
  - позиції чи ордери не сходяться з брокером;
  - брокер повернув ≥ 3 помилки поспіль;
  - спрацював тижневий ліміт збитку або ліміт кількості ордерів.
- **У паузі** рушій продовжує збирати дані, звірятися і показувати сигнали, але не відправляє ордери на вхід. Підтягування стопів і виходи за сигналом у паузі **дозволені**, бо вони зменшують ризик. Аварійна зупинка забороняє і їх, доки користувач не відновить роботу.

### 9.4 Надійність
- Стан (наміри, статуси, журнал) зберігається в SQLite транзакційно, до відправки ордера.
- Під час старту рушій спочатку виконує звірку з брокером і тільки потім відновлює розклад.
- Захисні стопи стоять у брокера, тому вимкнений рушій не залишає позиції без захисту.

### 9.5 LLM-фільтр
- **Модель за замовчуванням:** `claude-haiku-5-5`, налаштовується.
- **Вхід:** тікер, назва, короткий опис сигналу, до 20 новин за 7 днів (заголовок, дата, короткий зміст) з Alpaca News API.
- **Вихід:** структурований (через tool use / JSON schema) у форматі `{ verdict: allow|caution|block, reasons: [..], key_events: [..] }`. Якщо відповідь не розбирається, вона трактується як помилка.
- `caution` у режимі «з підтвердженням» показується з позначкою. У режимі «авто» поведінка налаштовується, за замовчуванням угода дозволяється.
- **Кеш:** один вердикт на (символ, дата сигналу).
- **Ліміти витрат:** за замовчуванням $1 на день і $20 на місяць. Облік ведеться за `usage` з відповідей API.
- **Помилка, ліміт або недоступність:** нових входів того дня немає (налаштовується). Виходи і стопи від фільтра не залежать.
- **Захист від маніпуляцій.** Текст новин вважається недовіреним. Фільтр може лише **заборонити** вхід, сигнал, створений правилами, але ніколи не створює угоду і не змінює її параметри. Тому найгірший наслідок підробленої новини — пропущений блок, а не нова угода.

### 9.6 Фільтр звітів
- **Джерело:** Finnhub earnings calendar.
- **Правило:** звіт протягом 3 торгових днів від дня сигналу → блок.
- **Джерело недоступне:** нових входів немає (налаштовується).

### 9.7 Секрети і доступ
- Ключі Alpaca, Anthropic і Finnhub та токен API зберігаються у Windows Credential Manager (крейт `keyring`). У файлах конфігурації та логах їх немає. Логер маскує секрети.
- Локальний API слухає лише `127.0.0.1` і вимагає токен.

### 9.8 Перший запуск
Застосунок показує вікно з попередженням: це інструмент автоматизації, а не фінансова порада; торгівля пов'язана з ризиком збитків; частина 1 працює лише на paper-рахунку. Без підтвердження далі не пройти.

## 15. Обробка помилок

- **Помилки:** крейти мають типізовані помилки (`thiserror`), `anyhow` використовується лише в бінарниках. Помилки адаптерів поділяються на тимчасові (повторювати) і постійні (не повторювати).
- **Повтори:** безпечні запити повторюються зі зростаючою паузою. Після збою відправки ордера спершу виконується пошук за `client_order_id`.
- **Дані:** тікер із пропусками в даних, нульовим обсягом чи нелогічними цінами (`high < low`) пропускається з записом у журнал.
- **Падіння кроку циклу** не зупиняє рушій. Крок отримує статус `failed` у `cycle_runs`, користувач отримує сповіщення. Кроки, що залежать від нього, пропускаються.
- **Логи:** `tracing`, файли з денною ротацією (зберігаються 30 днів), рівень налаштовується. Важливі події дублюються в `events`.

## 17. Результати перевірки під час планування (2026-11-04)

1. **Alpaca.**
   - Безкоштовний план дає історичні свічки всього ринку (`feed=sip`) з 2016 року, якщо кінець запиту щонайменше на 15 хвилин у минулому. Для аналізу о 16:30 ET цього досить.
   - Остання ціна для перевірки перед відправкою береться з `feed=iex`.
   - Класи ордерів `oto` і `bracket` з `time_in_force = day` є в документації.
   - Що ордери, подані до відкриття, приймаються, а новини доступні на безкоштовному плані, офіційно не підтверджено. Це перевіряють ручні тести з ключами користувача (план, «Передумова» і Task 13).
2. **Finnhub.** Ліміт безкоштовного плану — 60 запитів на хвилину. Чи входить календар звітів (зокрема історичний) у безкоштовний план, не підтверджено. Користувач перевіряє це своїм ключем до початку роботи над адаптерами; якщо календар платний, рішення ухвалюється разом із ним.
3. **Oxfmt** форматує CSS, SCSS і JSON сам, а HTML-шаблони Angular (`*.component.html`) — через вбудований Prettier. Для цього потрібен npm-пакет `oxfmt`, а він у проєкті є. Прогалин немає.
4. **`tauri-specta`** досі в стадії release candidate (rc.26), тому замість нього використовуємо `ts-rs` 12.
5. **Версії:** Angular 22, Tauri 2.12 (3.0 ще в альфі, не використовуємо), Rust 1.98.1, Node 24, pnpm 12.

## 18. Критерії готовності частини 1

1. `pnpm check` проходить без помилок.
2. Бектест обох стратегій на списку за період від 10 років формує звіт з метриками навчального і перевірочного періодів, бенчмарком SPY і блоком обмежень.
3. Рушій без нагляду проходить щоденний цикл на Alpaca paper протягом 5 торгових днів поспіль без незапланованих помилок, хоча б один день у кожному режимі.
4. У режимі «з підтвердженням» угода схвалюється з UI і виконується. Непідтверджена угода отримує статус `expired`.
5. Аварійна зупинка на paper скасовує ордери і ставить рушій на паузу. Закриття позицій працює за вибором.
6. Перезапуск рушія посеред відправки не створює дублікатів ордерів (автотест і ручна перевірка).
7. Для кожного рішення за ці 5 днів журнал показує повний ланцюжок з поясненнями.
